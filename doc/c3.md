# C3 : Produto

## 3.1 Desenvolvimento

### Stack tecnológica

O frontend está construído sobre Vite com React 18. Optei por Vite em vez do tradicional Create React App porque o CRA foi descontinuado pela equipa do React em fevereiro de 2023 e a documentação oficial recomenda agora Vite como sucessor. Em termos práticos o resultado é semelhante mas o Vite tem hot reload bastante mais rápido e bundles de produção mais pequenos.

Para o estilo escolhi Tailwind CSS, mas na versão 3 em vez da 4 (lançada em janeiro de 2025). A v4 introduziu mudanças significativas na configuração e ainda tem pouca documentação acumulada. Para um trabalho com prazo apertado, valeu a pena ficar pela v3 que tem três anos de tutoriais, Stack Overflow e outros sites.

Para o routing usei react-router-dom v6 com o padrão `Outlet` para layouts partilhados. Para os pedidos HTTP escrevi um wrapper próprio em cima do `fetch` nativo (cerca de 50 linhas em `src/api/client.js`), que trata automaticamente das credenciais, da serialização JSON e dos erros. Não usei axios porque o que precisava era simples e não justificava acrescentar uma dependência.

O estado de autenticação é mantido num `AuthContext` global. No arranque chama `GET /auth/me` para hidratar e expõe `login()`, `logout()` e `refresh()` a qualquer componente via o hook `useAuth()`.

### Arquitetura

A aplicação tem dois modos de execução: desenvolvimento e produção. As arquiteturas são diferentes.

#### Em desenvolvimento

![Arquitetura de desenvolvimento](images/07-architecture-dev.png)

O frontend corre no Vite na porta 5173 com hot reload ativo. A API é uma cópia (imagem) da `locky-api-m2` puxada do DockerHub e exposta na porta 3001 do host. A base de dados MySQL fica num container separado, com o seu volume persistente. Os pedidos do frontend para a API são cross-origin (portas diferentes), o que obrigou a configurar CORS com credentials e cookies SameSite=Lax.

#### Em produção

![Arquitetura de produção](images/08-architecture-prod.png)

Em produção apenas a porta 80 é exposta. Atrás dela está um container Nginx que faz duas coisas: serve os ficheiros estáticos da build do React e faz proxy de `/api/*` e `/auth/*` para o container da API, que fica numa rede interna do Docker e não está acessível do exterior. O resultado é que, do ponto de vista do browser, tudo vem da mesma origem (`http://localhost`), o que elimina por completo a complexidade de CORS.

### Estrutura do código-fonte

```
src/
  api/
    client.js (wrapper de fetch)
  components/
    Layout.jsx (navbar + outlet)

    PrivateRoute.jsx (protege rotas autenticadas)
    ConfirmDialog.jsx (modal reutilizável para confirmações)
    StationFormDialog.jsx (form modal criar/editar estação)
    LockerFormDialog.jsx (form modal criar/editar cacifo)
    ManageNav.jsx (sub-nav das páginas de gestão)
  context/
    AuthContext.jsx (provider global de autenticação)
  hooks/
    useAuth.js (hook que consome o contexto)
  pages/
    HomePage.jsx (lista pública de estações)
    StationDetailPage.jsx (detalhe da estação com cacifos)
    LoginPage.jsx (card com botão GitHub)
    DashboardPage.jsx (reservas do utilizador atual)
    NewReservationPage.jsx (formulário com cálculo de preço)
    ReservationDetailPage.jsx (detalhe; trata 403 e 404)
    EditReservationPage.jsx (só edita datas (limitação da API))
    ManageStationsPage.jsx (tabela + CRUD em modal)
    ManageLockersPage.jsx (tabela com filtro por estação)
    NotFoundPage.jsx (catch-all 404)
  App.jsx (BrowserRouter + Routes)
  main.jsx (entry point (envolve em AuthProvider))
  index.css (diretivas do Tailwind + body styles)
```

## 3.2 Instalação

### Pré-requisitos

* [Docker Desktop](https://www.docker.com/products/docker-desktop) instalado e a correr
* Conta GitHub (para autenticação via OAuth) e uma OAuth App registada com callback URL `http://localhost/auth/github/callback` (para o modo de produção)

### Configuração

Antes de arrancar é preciso criar um ficheiro `.env` na raiz do `locky-client/` com as variáveis abaixo. O `.env.example` no repositório serve de modelo:

```
VITE_API_URL=http://localhost:3001

DB_NAME=lockyapi
DB_USER=locky
DB_PASSWORD=lockypass
DB_ROOT_PASSWORD=rootpass

SESSION_SECRET=alguma-string-longa-e-aleatoria
GITHUB_CLIENT_ID=preencher
GITHUB_CLIENT_SECRET=preencher
```

`GITHUB_CLIENT_ID` e `GITHUB_CLIENT_SECRET` vêm da OAuth App registada no GitHub (Settings -> Developer settings -> OAuth Apps -> New OAuth App).

### Arranque

Para o modo de produção (com Nginx, default):

```bash
docker compose up
```

Para o modo de desenvolvimento (com Vite hot reload):

```bash
docker compose -f docker-compose.dev.yml up
```

Na primeira vez o Docker faz pull das imagens do DockerHub:
* [`inf25dw2g02/locky-api-m2:latest`](https://hub.docker.com/r/inf25dw2g02/locky-api-m2)
* [`inf25dw2g02/locky-client:latest`](https://hub.docker.com/r/inf25dw2g02/locky-client)
* `mysql:8.0`

A base de dados é populada automaticamente na primeira boot pela API. Os logs vão mostrar uma linha do tipo `Seed automatico: 30 stations, 90 lockers, 30 users, 30 reservations.`. Em restarts subsequentes a API detecta que a base de dados já tem dados e faz skip do seed.

## 3.3 Utilização

Em produção a aplicação fica acessível em <http://localhost>. Em desenvolvimento em <http://localhost:5173>.

A página inicial é pública e mostra a lista de estações. Clicando numa estação abre o detalhe com os cacifos disponíveis. Para reservar é preciso estar autenticado.

A autenticação é via GitHub. O botão "Entrar com GitHub" leva ao fluxo de OAuth: o utilizador é redirecionado para o github.com, autoriza a aplicação, e regressa autenticado. A API guarda a sessão num cookie HttpOnly.

Após login, a navbar passa a mostrar o nome de utilizador e três opções: Dashboard (lista das próprias reservas), Gestão (administração de estações e cacifos) e Sair.

No formulário de criar reserva, à medida que se escolhe um cacifo e se definem as datas, o preço total é calculado em tempo real (`pricePerHour * horas`). Submeter chama `POST /api/reservations` na API e redireciona para o dashboard.

## 3.4 Detalhes de implementação

### Cumprimento dos objetivos mínimos

| Objetivo | Como foi cumprido |
| :--- | :--- |
| Frontend React que consome a API do M1 | LockyClient comunica com a `locky-api-m2` (fork do M1) por todos os endpoints documentados no capítulo 2 |
| Autenticação federada | OAuth2 com GitHub, sessão por cookie HttpOnly |
| Páginas públicas | Homepage com lista de estações e detalhe de cada estação com cacifos |
| Área autenticada | Dashboard, formulários CRUD de reservas e páginas de gestão de estações/cacifos |
| Docker dev e prod separados | `docker-compose.yml` (prod) e `docker-compose.dev.yml` (dev), com configurações distintas para cada |
| Single command | `docker compose up` arranca tudo (DB + API + Nginx) com auto-seed na primeira boot |
| Imagens públicas no DockerHub | `inf25dw2g02/locky-api-m2` e `inf25dw2g02/locky-client` |
| Healthcheck no MySQL + depends_on | `condition: service_healthy` garante que a API só arranca depois da DB estar pronta |

### Elementos de valorização

* **Multi-stage Dockerfile** para a imagem de produção: stage 1 com Node faz a build do React, stage 2 com Nginx serve os ficheiros estáticos.
* **Nginx como proxy reverso** em produção: serve a SPA e faz proxy para a API. Elimina CORS em produção e mantém a API protegida da exposição direta.
* **Auto-seed na primeira boot** da API: a API verifica se a tabela `stations` está vazia e popula automaticamente na primeira execução.
* **ConfirmDialog reutilizável** para todas as confirmações destrutivas (cancelar reserva, remover estação, remover cacifo). Evita o `window.confirm()` nativo, que tem aparência inconsistente entre browsers.
* **Hidratação tolerante a falhas**: o `AuthContext` trata especificamente o caso de 401 (utilizador não autenticado) como estado válido, e não como erro. Outros códigos de erro são logados na consola mas não partem a aplicação.

### Dificuldades encontradas

A parte de Docker em produção deu bastante mais trabalho do que estava à espera.

O primeiro grande tropeço foi com cookies. Como o frontend (porta 5173) e a API (porta 3001) são cross-origin do ponto de vista CORS, configurei o cookie de sessão com `SameSite=None; Secure`. Tudo parecia bem no Chrome mas no Firefox o login não persistia. Depois de algum tempo a olhar para o DevTools percebi que era a Total Cookie Protection do Firefox a isolar o cookie. A solução foi mudar para `SameSite=Lax`, que funciona porque ambas as portas partilham o mesmo eTLD+1 (`localhost`).

Outra coisa estranha foi quando passei para produção com Nginx. Em dev o wrapper de fetch usava `import.meta.env.VITE_API_URL || 'http://localhost:3001'`. Em produção queria que `VITE_API_URL` ficasse vazio para os pedidos serem relativos (Nginx faz o resto). Mas o operador `||` trata a string vazia como falsy e cai no fallback. Resultado: o browser em produção a tentar pedidos cross-origin para `localhost:3001`, que nem está exposto. Trocar `||` por `??` (nullish coalescing) resolveu, porque o `??` só cai no fallback para `null` ou `undefined`.

Depois apareceu o problema do cookie `Secure`. Configurei `secure: true` quando `NODE_ENV=production`, mas como não tenho HTTPS no ambiente de produção académico (corre sobre HTTP localhost), alguns browsers gravavam o cookie mas não o enviavam de volta em pedidos subsequentes. Mudei para `secure: false` (com nota no código a documentar que num deploy real seria `true`). Acrescentei também `app.set('trust proxy', 1)` no Express, necessário quando a aplicação está atrás de um proxy.

Em vários momentos apareceram erros de "network not found" ou "container name already in use" entre tentativas, devido a redes e containers órfãos do Docker. A solução foi sempre limpar o estado com `docker compose down -v --remove-orphans`, `docker network prune -f` e em alguns casos reiniciar o Docker Desktop.

Houve também uma situação de cache: tinha publicado a imagem da API antes de incluir o auto-seed, e o `docker compose up` puxava do DockerHub uma versão desatualizada que não populava a DB sozinha. Foi preciso rebuild local, validar, e voltar a fazer push.

Por último, uma limitação que aceitei sem resolver totalmente: cada OAuth App do GitHub só aceita uma callback URL. Em dev é `http://localhost:3001/auth/github/callback` e em produção é `http://localhost/auth/github/callback`. Alternar entre os dois modos obriga a mudar manualmente na OAuth App, ou criar uma segunda app dedicada à produção. Para a entrega ficou configurada para produção.

### Limitações conhecidas

* Não existe distinção de papéis. Qualquer utilizador autenticado tem acesso à área de gestão. A API herdada do M1 não tem o conceito de admin, e adicioná-lo iria para além do âmbito deste M2.
* Não existe paginação na lista de estações. Como o seed cria 30 estações isto não é problema, mas seria necessário para um deploy real.
* Não existem testes automatizados.
