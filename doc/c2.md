# C2 : Recursos

Este capítulo descreve os recursos da API que o frontend consome e o processo de adaptação da API do M1 para suportar este novo cliente.

## 2.1 Recursos consumidos

A API da LockyAPI expõe quatro grupos de recursos: autenticação, estações, cacifos e reservas. O frontend usa-os todos.

### Autenticação (`/auth`)

| Método | Endpoint | Autenticado | Uso no frontend |
| :--- | :--- | :---: | :--- |
| GET | `/auth/github` | não | botão "Entrar com GitHub" faz `window.location.href` para esta rota |
| GET | `/auth/github/callback` | não | o GitHub redireciona para aqui; é a API que processa, define o cookie e redireciona para a SPA |
| GET | `/auth/me` | sim | `AuthContext` chama isto na inicialização para hidratar o estado do utilizador |
| GET | `/auth/logout` | sim | botão "Sair" na navbar |

### Estações (`/api/stations`)

| Método | Endpoint | Autenticado | Uso no frontend |
| :--- | :--- | :---: | :--- |
| GET | `/api/stations` | não | homepage e formulário de criar reserva |
| GET | `/api/stations/:id` | não | página de detalhe (inclui cacifos aninhados) |
| POST | `/api/stations` | sim | página `/manage/stations` |
| PUT | `/api/stations/:id` | sim | página `/manage/stations` |
| DELETE | `/api/stations/:id` | sim | página `/manage/stations` |

### Cacifos (`/api/lockers`)

| Método | Endpoint | Autenticado | Uso no frontend |
| :--- | :--- | :---: | :--- |
| GET | `/api/lockers` | sim | página `/manage/lockers` (com `station` aninhada) |
| GET | `/api/lockers/:id` | sim | usado quando se chega ao formulário de reserva via `?lockerId=X` (vindo do botão "Reservar" do detalhe de uma estação) para descobrir a estação correspondente |
| POST | `/api/lockers` | sim | página `/manage/lockers` |
| PUT | `/api/lockers/:id` | sim | página `/manage/lockers` |
| DELETE | `/api/lockers/:id` | sim | página `/manage/lockers` |

### Reservas (`/api/reservations`)

| Método | Endpoint | Autenticado | Uso no frontend |
| :--- | :--- | :---: | :--- |
| GET | `/api/reservations` | sim | dashboard (lista as reservas do utilizador autenticado) |
| GET | `/api/reservations/:id` | sim (e tem que ser dono) | página de detalhe da reserva |
| POST | `/api/reservations` | sim | formulário de criar reserva |
| PUT | `/api/reservations/:id` | sim (dono) | formulário de editar reserva (só altera datas) |
| DELETE | `/api/reservations/:id` | sim (dono) | botão cancelar na lista do dashboard e no detalhe |

## 2.2 Processo de adaptação da API do M1

A API do M1 (`locky-api`) foi pensada para funcionar standalone, sem frontend dedicado. Para a integrar com o frontend do M2 foram necessárias algumas alterações. Em vez de modificar o repositório do M1, que já tinha sido avaliado, fiz um fork chamado `locky-api-m2` ([github.com/UMAIA-DWEB/locky-api-m2](https://github.com/UMAIA-DWEB/locky-api-m2)) onde apliquei as alterações.

As principais mudanças foram:

**CORS com credentials.** No M1 a configuração era `app.use(cors())` sem opções, o que permite qualquer origem mas não envia cookies. Mudei para uma whitelist explícita lida da variável `CORS_ORIGIN` e ativei `credentials: true`. Sem isto, o browser não envia o cookie de sessão em pedidos cross-origin.

**Callback OAuth para a SPA.** No M1 o callback do GitHub redirecionava o utilizador para `/auth/me` (uma rota da própria API). No M2 mudei para redirecionar para o frontend (`FRONTEND_URL`), que é onde a SPA está alojada. Em dev é `http://localhost:5173`, em produção é `http://localhost`.

**Cookie de sessão com `SameSite=Lax`.** Configurei inicialmente `SameSite=None` por pensar que era preciso para cross-origin. O Firefox bloqueava silenciosamente o cookie devido à 'Total Cookie Protection'. Mudei para `Lax`, que funciona porque `localhost:5173` e `localhost:3001` são same-site (mesmo eTLD+1). Foi um dos bugs mais subtis de descobrir.

**Trust proxy em produção.** Em produção a API corre atrás do Nginx. Sem `app.set('trust proxy', 1)` no Express, os headers `X-Forwarded-*` que o Nginx envia não são reconhecidos. Para o cookie funcionar sobre HTTP localhost (sem certificado SSL) mantive `secure: false`. Num deploy real com HTTPS isto teria que ser `true`.

**Auto-seed na primeira boot.** A API verifica no arranque se a tabela `stations` está vazia. Se estiver, popula automaticamente com 30 estações, 90 cacifos, 30 utilizadores e 30 reservas. Em restarts subsequentes detecta dados existentes e faz skip. O script de seed manual (`npm run seed`) continua disponível para fazer reset completo.

**Include de relações nas respostas de reservas.** Os endpoints `GET /api/reservations` e `GET /api/reservations/:id` passaram a incluir o `locker` e a respetiva `station` aninhados. Sem isto, o dashboard teria que fazer N pedidos extra para mostrar o nome da estação de cada reserva.

**Correção do `totalPrice` na edição.** Em paralelo encontrei um bug do M1 em que o `PUT /api/reservations/:id` mudava as datas mas não recalculava o `totalPrice`. Corrigi também isso no `locky-api-m2`.
